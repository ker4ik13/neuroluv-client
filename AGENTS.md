# Инструкции проекта

## Тип проекта

Это фронтенд-проект, подключённый к Directus как headless CMS / админ-панели.

Сайт должен поддерживать динамический контент, управляемый через Directus:

- страницы;
- переиспользуемые блоки страниц;
- навигацию;
- SEO-метаданные;
- формы;
- медиафайлы;
- секции услуг, товаров, статей и другого контента.

Directus является основным источником контента. Фронтенд должен безопасно, предсказуемо и эффективно отображать данные из Directus.

## Главные цели

- Чистая архитектура.
- Feature-Sliced Design там, где это уместно.
- Переиспользуемый UI и бизнес-логика.
- Быстрая загрузка сайта и низкая нагрузка во время работы.
- Хорошее SEO по умолчанию.
- Хороший UX по умолчанию.
- Поддерживаемая система динамических страниц из Directus.
- Минимум лишних зависимостей.
- Понятные названия и предсказуемая структура файлов.

## Архитектура

Используй принципы Feature-Sliced Design:

- `app` — инициализация приложения, провайдеры, роутинг.
- `styles` - глобальные стили, шрифты.
- `pages` — композиция страниц на уровне маршрутов.
- `widgets` — крупные самостоятельные UI-секции.
- `features` — пользовательские действия и бизнес-функции.
- `entities` — бизнес-сущности: page, post, service, product, user, form и другие.
- `shared` — переиспользуемый UI-kit, API-клиенты, конфиги, библиотеки, хелперы.

Соблюдай правило зависимостей:

- Верхние слои могут импортировать нижние.
- Нижние слои не должны импортировать верхние.
- Избегай импортов между слайсами одного уровня.
- Предпочитай публичные API через `index.ts`.

Не создавай лишние FSD-слои для маленького изолированного кода. Начинай проще и выноси код в отдельные слои только тогда, когда появляется переиспользование или чёткая зона ответственности.

## Стиль кода

- Используй TypeScript строго.
- Предпочитай named exports.
- Делай небольшие компоненты с понятными props.
- UI-компоненты по возможности должны быть презентационными.
- Выноси data fetching, mapping, validation и бизнес-логику из UI-компонентов, если они разрастаются.
- Избегай magic strings. Используй константы, enum, схемы или типизированные мапы.
- Не создавай огромные файлы `utils` со всем подряд. Группируй хелперы по доменам: `date`, `seo`, `directus`, `format`, `url` и так далее.
- Не создавай непонятные абстракции. Абстракция должна уменьшать дублирование или изолировать реальную сложность.

## Интеграция с Directus

- Directus SDK / client должен находиться в `shared/api/directus` или в другом согласованном месте внутри shared API.
- Типы и схемы коллекций Directus должны быть типизированы.
- Не размазывай работу с сырыми ответами Directus по множеству UI-компонентов.
- При необходимости преобразуй ответы Directus в удобные frontend-модели.
- По возможности валидируй данные динамических блоков перед рендерингом.
- Неизвестный тип блока не должен ломать страницу. В development можно показать безопасный fallback, в production — скрыть или безопасно залогировать.
- Рендеринг страниц должен использовать registry / map блоков, а не большие дублирующиеся условные конструкции.
- SEO-поля должны быть типизированы и обрабатываться единообразно.

## Динамические страницы и блоки

Динамические страницы должны строиться вокруг такой модели:

- Коллекция `pages` содержит данные уровня страницы: title, slug, SEO, status, blocks.
- Блоки являются переиспользуемыми коллекциями Directus.
- У каждого блока есть соответствующий frontend-компонент.
- Центральный block renderer связывает имена блоков из Directus с frontend-компонентами.
- Каждый компонент блока отвечает только за собственный рендеринг.
- Общие UI-примитивы находятся в `shared/ui`.
- Переиспользуемые секции страниц находятся в `widgets`.

При добавлении нового блока:

1. Добавь или обнови тип Directus.
2. Добавь frontend-компонент.
3. Добавь блок в registry.
4. Обработай пустые состояния и ошибки.
5. Проверь SEO, accessibility, адаптивность и производительность.

## SEO-требования

Для каждой страницы нужно учитывать:

- уникальный title;
- meta description;
- canonical URL, если нужен;
- Open Graph-данные;
- правильную иерархию заголовков;
- семантическую HTML-разметку;
- alt-тексты у изображений;
- контент, доступный для индексации;
- чистые slug;
- отсутствие важного контента, который доступен только через client-side интерактив.

Не создавай страницы, которые выглядят хорошо визуально, но слабы для SEO.

## UX-требования

Проектируй удобство с самого начала:

- состояния загрузки;
- пустые состояния;
- состояния ошибок;
- disabled-состояния;
- hover/focus-состояния;
- mobile-first адаптив;
- доступные кнопки, ссылки, формы, labels и keyboard navigation;
- предсказуемая навигация;
- минимальный layout shift.

Если реализуешь формы:

- добавляй client-side валидацию там, где это полезно;
- показывай понятные сообщения об ошибках;
- предотвращай повторную отправку;
- обрабатывай success и failure состояния.

## Производительность

- Избегай лишнего client-side JavaScript.
- Предпочитай server-side или static rendering, если фреймворк это поддерживает.
- Не запрашивай из Directus больше полей, чем нужно.
- Используй оптимизацию изображений.
- Lazy-load для тяжёлых неключевых компонентов.
- Не добавляй большие зависимости ради маленьких задач.
- Используй memoization только там, где есть реальная причина.
- Избегай лишних re-render.
- Следи за размером bundle.

## Стилизация

- Следуй существующему подходу к стилям.
- Предпочитай переиспользуемые design tokens и shared UI-примитивы.
- Не хардкодь случайные отступы, цвета, размеры шрифтов и брейкпоинты, если в проекте уже есть токены.
- Делай адаптивное поведение осознанным.
- Не создавай устаревший визуальный стиль. Интерфейс должен быть современным, чистым и аккуратным.

## Перед внесением изменений

Перед реализацией изучи текущую структуру:

- package manager;
- framework;
- подход к роутингу;
- подход к стилизации;
- Directus client / schema;
- существующую FSD-структуру;
- существующие shared UI-компоненты;
- доступные scripts.

Не предполагай стек проекта, если его можно проверить в репозитории.

## Проверка

Перед завершением задачи запусти самые релевантные доступные проверки:

- typecheck;
- lint;
- tests;
- build.

Если команду нельзя запустить, объясни почему и напиши, что нужно проверить вручную.
